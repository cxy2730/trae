第二部分: PE 导入系统分析
===============================================================================

2.1 标准 PE 导入系统 (已被破坏)

  Import Directory RVA: 0x1000 (指向 .text, 非法!)
  IAT Directory RVA: 0x0 (零值, 不存在标准 IAT)
  IAT 区域 (0x2BA488E-0x2BA65EC): 存放加密垃圾数据

  IAT 示例值:
    midiStreamRestart @ 0x2BA488E: 0x12ECFA51 (非函数指针!)
    GetProcAddress @ 0x2BA4AAE:   0xE3FC2C20 (非函数指针!)
    IsDebuggerPresent @ 0x2BA4A1A: 0xBC85B083 (非函数指针!)

  结论: KG.exe 使用自定义导入解析器, 而非 Windows PE 标准加载机制.

2.2 自定义导入解析器

  解析流程:
  1. 启动时扫描 .rdata 中的 API 名字符串
  2. 通过 LoadLibrary + GetProcAddress 动态获取函数地址
  3. 将解析结果填入 .rdata 中的分发表 (dispatch table)
  4. 代码通过两级间接调用访问这些函数

第三部分: 两级间接调用机制 (反编译核心)
===============================================================================

3.1 机制概述

  KG.exe 使用两级指针间接调用以逃避静态分析和 API 扫描:

  代码:   call dword ptr [0x4A258C]     (.text 段)
            ↓ 读取指针
  分发表:  0x4A258C 在 .rdata 段, 存放 0x02BA505E
            ↓ 读取函数地址
  IAT槽:  0x02BA505E 在 .data 段, 存放运行时解析的函数地址
            ↓ 执行
  目标函数: 由 GetProcAddress 在运行时解析

3.2 统计数据

  - FF 15 (call [imm32]) 指令总数: 2,829 条
  - 唯一分发表条目: 438 个
  - 高频调用目标 (Top 5):
    1. 0x02FE8D54: 894 次引用 (核心调度函数)
    2. 0x02FE9B54: 121 次引用
    3. 0x004A2564: 65 次引用
    4. 0x004A2558: 63 次引用
    5. 0x004A2544: 39 次引用

  - 代码中的函数 (基于 prologue 检测): 435 个
  - 标准 IAT 条目: 432 个 (均为加密垃圾值)

3.3 分发表数据流向

  .text 中的 call 指令 → .rdata 分发表 → .data IAT → 真实函数

  分发表存放的指针示例:
    0x4A258C → 0x02BA505E (IAT 槽位)
    0x4A2338 → 0x02BA4B04
    0x4A256C → 0x02BA50EA
    0x4A2354 → 0x02BA4A82

  注: 0x02BAxxxx 范围正好对应 .data 段末尾 (0x2BA7000-0x2BDD000)

  mov dword ptr [0x3010fcc], edx ; g_sys_low = HI(result)

  and ecx, 0xff
  mov dword ptr [0x3010fc8], ecx ; g_sys_mid1 = LO(result)
  
  shl ecx, 8
  add ecx, edx
  mov dword ptr [0x3010fc4], ecx ; g_sys_combined = (HI << 8) | LO

  mov dword ptr [0x3010fc0], eax ; g_sys_high = result >> 16

  push 1
  call 0x487396                  ; init_check1(result)

  call 0x486b5f                  ; comp3_init()
  call 0x485e1b                  ; main_logic()

  lea eax, [ebp - 0x5c]          ; 准备结构体参数
  push eax
  call dword ptr [0x4a21d4]      ; 分发表: init_params

  test byte ptr [ebp - 0x30], 1  ; 检查标志位

  call 0x490d7c                  ; main_dispatch(result)

7.3 卡密验证流程 (修正版)

  KG.exe 使用 ExuiKrnln 的 WebBrowser 控件进行卡密验证:

  1. KG.exe 调用 ExuiKrnln 初始化
  2. ExuiKrnln 创建嵌入式 WebBrowser (CEF)
  3. 浏览器加载卡密输入页面 (HTML/JS)
  4. 用户在 UI 中输入卡密
  5. 前端 JS 代码发送验证请求到服务器:
     - POST /api/register { "card_key": "xxxx" }
     - POST /api/valid { "card_key": "xxxx" }
     - POST /api/authenticate { "card_key": "xxxx", "token": "yyyy" }
  6. 服务器验证卡密有效性
  7. 返回 token 给客户端
  8. ExuiKrnln!SetCookie_WebBrowserEx() 存储 token
  9. Token 在后续通信中作为身份凭证

7.4 卡密绕过方案

  方案 A: JS 注入 (最简单)
    使用 ExuiKrnln!RunJsCmd_WebBrowserEx() 注入 JS 代码:
    
    // 注入的 JavaScript 代码
    // 1. 禁用前端验证
    window.validateCardKey = function() {
        return { success: true, token: "FAKE_TOKEN" };
    };
    // 2. 直接设置 cookie
    document.cookie = "auth_token=FAKE_TOKEN; path=/";
    // 3. 跳过验证页面
    window.location.href = "/authenticated.html";
    
    实现:
    ExuiKrnln_RunJsCmd_WebBrowserEx("
      window.validateCardKey = function() {
        return { success: true, token: 'FAKE_TOKEN' };
      };
      document.cookie = 'auth_token=FAKE_TOKEN';
    ");

  方案 B: Cookie 伪造
    使用 ExuiKrnln!SetCookie_WebBrowserEx() 直接设置认证 Cookie:
    
    ExuiKrnln_SetCookie_WebBrowserEx("auth_token", "FAKE_TOKEN");
    ExuiKrnln_SetCookie_WebBrowserEx("user_id", "FAKE_USER");

  方案 C: DevTools + 本地代理
    1. ExuiKrnln!ShowDevtools_WebBrowserEx() 打开 DevTools
    2. Chrome DevTools 中设置本地代理
    3. 使用 Proxy SwitchyOmega 或类似工具
    4. 将验证请求重定向到本地伪造服务器
    5. 本地服务器返回 { "success": true, "token": "FAKE" }

  方案 D: HTTP 拦截 (MITM)
    使用 Fiddler / Charles / mitmproxy 拦截:
    - 拦截 POST /api/register, /valid, /authenticate
    - 修改响应为 { "success": true, "token": "FAKE_TOKEN" }
    - 启用 HTTPS 解密 (安装根证书)

  方案 E: Skynet 协议分析
    ExuiKrnln 使用 Skynet 框架进行后端通信:
    - 分析 Skynet 协议格式 (LUA 序列化)
    - 伪造 Skynet 消息
    - 直接与后端通信 (需绕过服务端验证)
